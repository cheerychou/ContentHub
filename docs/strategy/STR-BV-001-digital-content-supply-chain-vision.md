# 企业级数字内容供应链系统（A-DCSC）愿景与项目章程

> **文档版本**：V1.0
> **创建日期**：2026-09-03
> **核心议题**：探讨在AIGC时代，企业如何构建一个覆盖内容"存储、制作、管理、分发"全链路的智能系统。
>
> **性质声明**：本文档由早期《数字内容供应链系统（讨论纪要）》蒸馏而来，作为现行**愿景与章程**权威出处保存；原始讨论纪要可经 git 历史（初始提交）追溯。

## 1. 项目背景与讨论缘起

在过去的20年中，内容数字化经历了从"载体转移"到"AI重构"的演变。随着AIGC的爆发，企业内容管理（ECM）正从静态的"档案柜"向智能的"供应链"转型。

本次讨论的核心出发点，是解决企业在多渠道分发（如公众号、抖音等）场景下，面临的**内容资产混乱、血缘关系丢失、改版影响面难以评估**等痛点。

## 2. 核心定义：这是一套什么系统？

### 2.1 系统名称定义
我们将这套系统定义为：**AI-Native 智能内容供应链系统（AI-Native Digital Content Supply Chain, A-DCSC）**。

- **为什么是"供应链"**：因为它借鉴了制造业供应链的概念，管理内容从"原材料（底片）"到"零部件（半成品）"再到"成品（发布件）"的完整加工、流转与追溯过程。
- **为什么是"AI-Native"**：区别于传统系统后挂AI插件，该系统从底层的"底片识别"、中层的"智能编辑"到顶层的"即时渲染"都深度嵌入了AI能力。

### 2.2 核心价值主张
- **传统CMS解决的是"内容发出去"的效率问题。**
- **A-DCSC解决的是"内容改起来"和"资产传下去"的确定性与合规性问题。**

## 3. 核心管理原则：三态分离模型

为了杜绝资产冗余，系统内将内容资产按生命状态划分为三个逻辑隔离的区域：

| 区域         | 称谓       | 存储对象                                                     | 管理重点                               |
| :----------- | :--------- | :----------------------------------------------------------- | :------------------------------------- |
| **素材区**   | **原子态** | 不可再生的"底片"（如RAW照片、独立录音干声、剪辑工程文件`.prproj`）。 | 确保唯一性、版权溯源、物理安全。       |
| **半成品区** | **编辑态** | 经过精修的"黄金母版"（如调色后的高精度JPG、定稿的Word文档）。 | 版本管理、质量标准、视觉焦点坐标记录。 |
| **制成品区** | **发布态** | **仅物理存储**需人工干预的特殊定稿。对于纯机械性的缩放/转格式，**只存储"渲染指令"**，由引擎实时生成。 | 渠道适配、分发元数据、CDN缓存策略。    |

## 4. "底片"定义的多元化指南

在落实三态分离时，不同媒介的"底片"（即素材区的准入标准）定义如下：

| 内容类型   | 底片（必须存入素材区的文件）                                 | 半成品示例                       | 制成品示例                           |
| :--------- | :----------------------------------------------------------- | :------------------------------- | :----------------------------------- |
| **图片**   | 单反/扫描仪直出的 `.RAW` / `.ARW`                            | 调色/裁切后的高精度全尺寸 `.JPG` | 带人工排版文字的公众号封面 `.JPG`    |
| **文本**   | **情况A**：带修订记录的 `.docx`<br>**情况B**：含Prompt的对话日志 `.json`<br>**情况C**：原始录音 `.wav` | 定稿的 `.docx` / Markdown        | 导出的公众号 `.html` 或 `.pdf`       |
| **短视频** | **必须同时存三样**：<br>1. 视觉层：高码率原始 `.mov`<br>2. 音频层：独立录制的 `.wav` 干声<br>3. 逻辑层：剪辑工程文件 `.prproj` | 压制了字幕但未调色的代理文件     | 针对抖音/视频号渲染的不同码率 `.mp4` |

## 5. 系统能力边界与四层架构

系统采用分层架构设计，但这**不代表必须一次性建设完毕**，而是为了支持模块化、渐进式的落地。

```text
+-----------------------------------------------------------------------+
|                    【业务应用层】 - 能力出口与消费端                      |
|   (微信公众号/H5)   (抖音/视频号)   (印刷出版)   (AI对话/大模型调用)      |
+-----------------------------------------------------------------------+
                                      ^ (API网关/内容分发)
+-----------------------------------------------------------------------+
|               【统一内容服务层】 - 智能检索与知识推理                      |
|  +------------------+   +-------------------+   +-------------------+  |
|  | 语义搜索引擎 (AI) |   | 血缘关系图谱引擎  |   | 即时渲染/转码引擎 |  |
|  | (多模态向量检索)  |   | (影响面分析)      |   | (缓存与指令执行)  |  |
|  +------------------+   +-------------------+   +-------------------+  |
+-----------------------------------------------------------------------+
                                      ^ (元数据/指令触发)
+-----------------------------------------------------------------------+
|              【内容生产加工层】 - 智能编辑与制作（核心价值区）             |
|  +------------------+   +-------------------+   +-------------------+  |
|  | 智能编辑 (AIGC)   |   | 自动化转码/裁剪   |   | 版本迭代管理     |  |
|  | (调色/去噪/扩写)  |   | (横竖屏转换/压缩) |   | (时间线追溯)     |  |
|  +------------------+   +-------------------+   +-------------------+  |
+-----------------------------------------------------------------------+
                                      ^ (读写资产)
+-----------------------------------------------------------------------+
|               【数字资产存储层】 - 三态分离的物理/逻辑存储                  |
|  +------------------+   +-------------------+   +-------------------+  |
|  | 素材区 (原子态)   |   | 半成品区 (编辑态)  |   | 制成品区 (发布态) |  |
|  | (RAW/工程文件)    |   | (黄金母版/定稿)    |   | (指令集/人工特殊版)|  |
|  +------------------+   +-------------------+   +-------------------+  |
+-----------------------------------------------------------------------+
```

## 6. 建设策略：分阶段演进，拒绝"一步到位"

尽管架构图展示了完整的蓝图，但实施路径必须是分阶段的：

- **第一期（MVP，侧重存储与血缘）**：
    - 落地"三态分离"逻辑。
    - 建立基础的**血缘关系记录**（如通过文件命名规范或Excel映射关系）。
    - **目标**：先让资产变得"干净、可追溯"。
- **第二期（增效，侧重AI加工）**：
    - 引入**智能编辑**工具（自动调色、智能裁剪）。
    - 建立**即时渲染引擎**，处理缩放、转格式等指令。
    - **目标**：大幅提高内容制作效率。
- **第三期（智能化，侧重图谱与语义检索）**：
    - 在积累了足够多的元数据和血缘关系后，引入**多模态向量搜索引擎**和**血缘图谱分析**。
    - **目标**：实现"语义级"检索和"影响面"预警（如改一张RAW，系统提示所有依赖它的成品）。

## 7. 产品战略选择：通用型 vs. 垂直型

在商业化定义上，系统定位将决定后续的发展方向：

| 定位             | 定义                                                         | 挑战与风险                                                   | 推荐度                                           |
| :--------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------- |
| **通用型工具**   | 服务所有行业，如百度网盘+AI、Canva。                         | 面临巨头红海竞争；AI基础能力商品化，难以建立数据飞轮。       | **不推荐**初创团队切入。                         |
| **垂直行业专家** | 深耕特定领域（如电商、工业、传媒），内置行业元数据模板（SKU、工艺参数）。 | 市场空间相对较小，但对客户业务绑定极深，**替换成本极高**，数据飞轮能构建AI护城河。 | **强烈推荐**。建议定位为"XX行业智能内容供应链"。 |

## 8. 产品定位（2026-09-04 定稿）

### 8.1 定位声明

> **ContentHub（A-DCSC）是面向 B2B 企业的内容供应链系统：让企业以"一份源资产 + 一套配方"的方式，管理从选题研究到多平台发布的内容全链路——单人可用、团队可扩展、生态可对接。**

### 8.2 第一用户与证据

第一个用户是**自有场景**：车嘀嗒（CDD3 数字化门店产品）运营方的内容营销——通过官网、公众号、抖音、视频号、bilibili 的持续内容生产创造销售线索。2026-09-04 实地盘点（自有内容库 122 篇笔记、CDD3 MK-005 差距分析、VidFlow 项目复盘）确认痛点真实且高频：同题多副本、封面多平台手工排版、流水线状态无追踪。单人生产不是协作问题的反证，而是协作问题尚未爆发的状态——产品须做到单人模式流程零负担，同时协作原语（角色/审核/状态机）从第一天就在数据模型里。

### 8.3 商业化三级路径

1. **自用**（M0-M1）：做自己的内容工厂，在真实周更节奏中磨产品；
2. **生态对接**（M2）：成为 CDD3 营销中心的上游——总部内容包下发至连锁门店（对接 MK-005 Phase 3 语义）；
3. **独立产品化**：汽车后市场 B2B 内容营销 SaaS——自有行业内容已建立的心智是天然冷启动资产。

交付形态与技术边界见 [PRD-MVP-001](../product/PRD-MVP-001-mvp-build-plan.md)（Web 自托管、配方派生引擎优先、自动化红线）；跨项目自动化教训见 [KNW-EXP-001](../knowledge/KNW-EXP-001-content-supply-chain-lessons.md)。
